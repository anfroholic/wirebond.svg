Fields, not files

We asked the KiCad developers where our bonding design should live inside a footprint. They said "footprint fields". This page shows what that means and what it changes for us.

In short
  • A footprint can carry two kinds of extra data: fields, which are short labelled lines of text, and embedded files, which are whole files tucked inside.
  • We put our whole design file, the .wb.svg, in as an embedded file of type "other". It works in KiCad 10.0.3, but nobody has promised it will keep working.
  • The developers pointed us at fields. Fields are documented, any name is allowed apart from ones starting with ki_, and KiCad carries them from the library onto the board.
  • We already use fields for a lot: wires, wire types, fiducials and die heights all travel as wb_… fields.
  • Decision: one hidden field, wb_svg, holding the whole .wb.svg exactly as written. The exchange format is the SVG, so the field is simply the SVG.
  • Tested in KiCad 10.0.3: designs of 378 to 653 KB came back byte for byte after KiCad re-saved the library and the board. The field stays hidden, and nothing got slower.
  • The design is smaller than the STEP model already in the same footprint: 386 KB against 1,059 KB.

1A footprint is a box with pockets

Think of a footprint as a box KiCad keeps for each part. It has three pockets, and KiCad treats each one differently.

An analogy. A field is a line on the shipping label: "Contents: die", "Made by: Wire Bond Bench". Anyone can read it without opening the box, and the carrier promises to keep the label on. An embedded "other" file is a letter taped inside the box. It arrives today, but the carrier never said it would keep letters, and it already throws some kinds away (fonts).

2What a field looks like

Fields have been part of KiCad footprints since version 8. Every footprint has four built-in fields (Reference, Value, Datasheet, Description), and you can add as many more as you like. KiCad keeps names starting with ki_ for itself; any other name is ours. A field can be hidden so it never shows on the board.

Because fields are KiCad's documented way to add data, other parts of KiCad can use them too: text on the board can show them, rule areas and design rules can test them, and scripts and plugins can read them. None of that works on an embedded file.

3Fields we already write

This isn't new ground. When the bench writes a board, the dies, every wire and the wire types already travel as hidden fields. The developers' advice is to do the same for the design that rides on a library footprint.

Many fields aren't a problem. The example board in examples/kicad/example.kicad_pcb (written by an older version of the exporter) carries 729 wb_ fields, and it opens in KiCad. The longest of them is 48 characters with its name. Lots of short fields is exactly how KiCad expects fields to be used.

5Is it too big?

So fields are the right pocket. Can we just put the whole .wb.svg into one field and be done? The worry was size. Most of a design file is the die picture, and the whole file is far bigger than anything fields normally hold. Section 7 has the answer from testing: KiCad copes fine.

The next chart sets those sizes beside the fields we write today. The scale jumps by ten times at each step; otherwise the field values would be too small to see.

What size could still affect. KiCad's file handling is fine with it (section 7). What hasn't been tried is KiCad's windows: the Footprint Properties table, the Properties panel, and Find all show or search field values. A 386,000-character value will at least be a wall of text there, and might be slow to open. That's the one thing left to check by hand.

Why B. The .wb.svg is meant to be the exchange format, so the simplest thing is to carry it unchanged. Anything that reads a .wb.svg can read the field, with no second format to design or keep in step. It sits in the pocket KiCad promises to keep. Section 7 shows that its size isn't a problem for KiCad: the STEP model next to it is bigger.

7How one field will look

Everything in this section comes from a real test. The example die was exported from the bench with its 3D model, the design was added as one field, and KiCad 10.0.3 (kicad-cli) re-saved, checked and plotted the result.

Its name: wb_svg

Not wb_design. Boards written by the bench already carry a board-level property called wb_design that holds the design's name (written in app/js/wbsvg.js). A reader that looks for the first wb_design would find the wrong one, and the first version of the test did exactly that. wb_svg says what's inside.

Only three things in the SVG are written differently inside the field. These are KiCad's rules for every quoted string, and KiCad undoes them when it reads the file:

In the .wb.svgIn the field
" (double quote)\"
\ (backslash)\\
a line break\n

Everything else is the SVG character for character, the die picture and seal included. Our exporter already escapes every field this way, with q() in app/js/export.js, and that's the function the test used.

In KiCad's window

On the board, the field is invisible: it's hidden, so it doesn't draw on F.Fab, and plots of the board came out no bigger with it than without.

In KiCad's windows it's one more row in the field table. Its value is the start of the SVG, cut off at the edge of the column. We haven't seen how KiCad's Footprint Properties, its Properties panel or its Find dialog behave with a value this long. That's the first thing to try by hand (section 8).

How it sits beside the STEP

You were right about the STEP: it already makes up most of the file, and the design is about a third of its size. This example design is 378 KB rather than the 112 KB of examples/example.wb.svg because the bench exports the die picture at a higher resolution.

Getting the design back out

  1. Open the footprint or board in the bench.The bench would find wb_svg and load the design directly. This is to build: today it reads our other wb_ fields, not this one.
  2. Copy it out of KiCad by hand.Footprint Properties, click the wb_svg value, select all, copy, and paste into a file named something.wb.svg. KiCad undoes the escapes when it reads the file, so the value should come out as plain SVG. Not tried yet.
  3. Take it straight from the file.Any language can do it: take the quoted text after (property "wb_svg" and undo the three escapes. In Python:
import re
text = open("chip_top.kicad_mod", encoding="utf-8").read()
value = re.search(r'\(property "wb_svg" "((?:[^"\\]|\\.)*)"', text)[1]
svg = re.sub(r'\\(.)', lambda m: "\n" if m[1] == "n" else m[1], value)
open("chip_top.wb.svg", "w", encoding="utf-8").write(svg)

Whichever way it comes out, the design carries its own seal (wb:data-sha256 and wb:drawing-sha256), so a reader can check that it is exactly what the bench wrote.

8What to do next

  1. Open a footprint with the field in KiCad.Look at Footprint Properties, the Properties panel and Find. Check that they open quickly, and that copying the value out gives back the .wb.svg.
  2. Write wb_svg in the exports.On the library die footprint and on the first die of a board from the bench: hidden, on F.Fab, with the same tiny font and the same escaping as our other fields. One per footprint, replaced on each export.
  3. Read it back.When the bench opens a .kicad_mod or .kicad_pcb that carries wb_svg, load the design from it and check its seal.
  4. Drop the embedded "other" file.The field does its job in the pocket KiCad promises to keep. The STEP stays an embedded file of type "model", as KiCad intends.
  5. Test the two stops we haven't tried.Run Update PCB from Schematic (with and without the "Remove footprint fields not found in symbols" box) and Update Footprints from Library on a board with our die, and check that wb_svg is still there afterwards.
